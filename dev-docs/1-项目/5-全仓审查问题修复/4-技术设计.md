# 全仓审查问题修复技术设计

> **状态：approved。** 本文是本项目唯一的权威技术设计入口，整合原总体技术设计入口的有效内容；旧入口已删除并纳入本期已批准决策。它定义待实施的契约与边界，不表示产品代码、测试、历史 UI 项或参考文档已经完成。安全整改仍明确不在本项目范围内。

## 背景与约束

### 已核验的源码基线

- **PC Web：**当前 `agentStore.ts` 默认指向 loopback，`agentApi.ts` 与 EventStream 读取可变地址；部分 TanStack Query key 不含目标 Agent。Settings 直接渲染查询快照，checkbox 变更会触发 `refetch()`；Launcher 现只读运行状态。
- **Android：**已有 `PowerScreen` 和 `PowerViewModel`，但导航尚未给出获批 IA 所需的“管理页 → 二级 Power”入口。`FilesViewModel` 的列表请求未以目录会话完整防护乱序/重复分页；`SharedEventStream` 未将重连传递为可消费对账信号。
- **Agent：**`AgentSettingsService.UpdateAsync()` 目前会先调用 AutoStart 再写用户配置，缺少 revision、单一写入口和可恢复失败语义；`FileListingEndpoints` 会物化完整可见列表后按 offset 截取；`EventEnvelope` 目前仅含 `type`、`payload`、`timestamp`。
- **工作树：**实施前必须重新核验相应源码、HEAD 和并行改动所有者；本文不授权覆盖其他工作。

### 架构约束

1. 不引入数据库、消息队列、新状态管理框架或跨 origin API 通道。
2. 不改变认证、CORS、LAN 策略、凭据、权限或远程关机的既有安全边界。
3. 设置文件与 Task Scheduler 不是可提供硬事务的同一资源；设计必须显式处理、记录和恢复部分失败。
4. WebSocket 只提供失效提示，不提供可重放的事实日志；HTTP snapshot 才是恢复后的权威。
5. 大目录 v2 在不建索引的约束下可以把额外内存限制为 `O(limit)`，但每页仍可能扫描目录，不能承诺 `O(log N)` 查找。

## 目标与非目标

### 目标

- PC Web 默认以自身同源 Agent 工作；用户切换目标时导航到目标 Agent，而不是发起跨 origin XHR/WS。
- Android 底栏固定五项：音频、文件、启动器、管理、设备；Power 从管理页风险操作卡进入二级路由。
- Agent 为完整逻辑设置提供 revision、ETag、If-Match 条件写、唯一仓储、恢复日志、外部副作用补偿和 v2 事件元数据。
- 文件分页引入可验证边界的 cursor v2，同时保留 v1 offset 兼容路径。
- 给出可直接实施和契约测试的 API、错误、迁移、降级与回滚约束。
- 历史 Android UI 延期项只建立台账并针对已有结论复验；除非台账记录的证据失效或产品另行立项，不将六类历史项整体重新打开为本期实现范围。

### 非目标

- 不重写启动器命令语义、文件路径安全规则、远程关机业务语义或安全模型。
- 不为 cursor v2 提供精确 `total`、服务端事件回放、跨实例事件顺序或目录索引。
- 不做 settings 的字段级三方自动合并；有结构性集合冲突时由用户重新加载后手工重放。
- 不将历史 UI 台账的“待复验”误写为“已修复”，也不把现有实现之外的体验承诺写入 current 文档。

## 设计方案

### ADR-01：PC Web 同源导航与缓存隔离

页面由 Agent 静态托管时，当前页面的 origin 就是默认受控 Agent：

```text
targetKey = new URL(window.location.origin).origin.toLowerCase()
REST      = /api/...
WS        = 从 window.location.origin 推导的同源 WebSocket URL
```

切换合法目标时只执行：

```ts
window.location.assign(targetOrigin + window.location.pathname + window.location.search + window.location.hash)
```

`targetOrigin` 必须是可规范化的 absolute `http` 或 `https` origin；包含 path、query、fragment、userinfo 或规范化后不是 origin 的输入在客户端拒绝。成功完成目标页的轻量 `GET /api/status` 后，才更新最近目标的 `origin`、展示名和最近核验时间；最多保留 10 项，且不保存业务数据、草稿或凭据。

所有 query key 的第一段必须是 `['agent', targetKey, ...]`。例如 settings 为 `['agent', targetKey, 'settings']`，目录为 `['agent', targetKey, 'files', rootId, path, generation]`。mutation 捕获发起时的 `targetKey`，回调只可更新同一 target；整页导航是首选隔离机制，若未来改为非导航切换，必须先取消/移除旧 target query、递增 epoch、关闭旧 socket，再启用新请求。

开发 Vite proxy 仅是本地开发适配器，不提供跨 Agent 选择能力；UI 必须明确其固定代理限制。此决定不改变安全边界。

### ADR-03：Android 五 Tab 与管理二级 Power

`AppDestination.entries` 只包含 Audio、Files、Launcher、Admin、Device 五个底栏目的地。Admin 首屏的“风险操作 / 远程关机”卡导航至 `Power(route="power")`；该 Power route 不属于底栏 entries。由该卡进入时，返回栈回到 Admin；深链或进程恢复若无有效上级栈，安全返回 Admin，而不是新增 Tab 或跳到 Device。

Power 页面进入时并发读取 status 与 shutdown status；只有 `capabilities.remoteShutdown == true` 且服务报告可用时才能打开确认。确认后才发出既有 POST。网络、409、503 显示可重试错误；WebSocket 断线、恢复或重进页面都不得自动重放关机 POST。管理页只能编辑 `remoteShutdown.enabled`，不得混合危险执行确认。

历史 UI 工作采用 `HUI-*` 台账：每条记录包含原延期项、已有证据链接/版本、复验方法、责任人、复验日期、结论（通过、仍阻塞、需独立立项）和关联 UX-AC。台账复验不创建“六项全部重做”的实现任务；只有复验失败的单项可成为新的、单独批准的工作。

### Settings draft 状态机

客户端首次读取 settings 后，创建不可变 `baseline` 与可编辑 `draft`；输入只改 `draft` 和 `dirtyPaths`，不得改 query cache 或因输入调用 refetch。保存使用 baseline 的 ETag；成功 PUT 响应同时替换 baseline/draft 并清除 dirty。远端 `settings.updated` 或重连对账的处理规则为：

| 本地状态 | 收到更高 revision | 行为 |
|---|---|---|
| clean | 是 | 合并 250 ms 内同类事件后 GET，新的 snapshot 成为 baseline/draft。 |
| dirty/saving | 是 | 保留输入，进入 conflict；不静默覆盖、不自动重放。 |
| conflict | 任意 | 只更新远端提示 revision；由用户选择丢弃并加载，或手工重放草稿。 |
| PUT 成功 | 相同 `operationId` 与 revision | 以 PUT body 为权威，可忽略稍后的重复事件。 |

文本与整数在 draft 中保留原始文本，保存前转换并进行本地校验。400、412、503 或网络失败均保留草稿。保存按钮仅在 `dirty && !saving && !conflict` 时可用。

### Android 文件会话

`ListingKey = (target, rootId, canonicalPath)`；每次 root/path 切换、刷新、匹配当前目录的文件事件或重连，都执行 `begin(key)`：取消初始和下一页 job、递增 generation、清空该会话的 entries/cursor/in-flight，并从首页开始。

请求捕获不可变的 key、generation、cursor；只有三者仍等于当前会话才可写状态。每个 cursor（首页使用专用 sentinel）最多一个 in-flight 请求；`loadMore` 还要求会话存在、`hasMore` 为 true、初始页未加载、当前未加载更多且 cursor 未完成。取消不显示为网络错误；下一页失败保留已接受 entries 与 cursor 并提供重试。404 root/path、409 `directory_changed`、410 `cursor_expired` 都废弃会话并提示从首页刷新，不展示为继续可加载的旧会话。

## 接口与数据流

### API-SET-01：版本化 Settings snapshot 与条件写

`GET /api/settings` 在既有字段上加性返回 `revision`，并返回强 ETag：

```http
ETag: "42"
Cache-Control: no-store
Content-Type: application/json
```

```json
{
  "revision": "42",
  "autoStartEnabled": true,
  "launcher": { "items": [] },
  "fileRoots": [],
  "remoteShutdown": { "enabled": true }
}
```

`revision` 是十进制非负整数字符串，客户端不得按 JavaScript number 处理。首次引入 metadata 的既有有效配置初始化为 `"1"`；每次**成功逻辑设置提交**恰好加一。ETag 的值严格为该 revision 的带引号强标签（例：`"42"`）；body revision 与响应 ETag 去引号后的值必须一致。

`PUT /api/settings` 保持既有 nullable patch body。已声明 `settingsRevision` capability 的客户端必须发送单个精确 header：

```http
If-Match: "42"
X-Operation-Id: 5ec8b1a7-8090-4f4f-a3a1-47d696f1f324
```

`If-Match: *`、多 ETag、弱 ETag、格式非法 revision 均为 `400 invalid_if_match`；服务端不会将其解释为无条件覆盖。`X-Operation-Id` 是客户端生成的 UUID，用于日志、响应和事件关联，服务端可在缺失时生成；它**不是**请求去重键，超时客户端必须 GET 对账而不是自动重发 PUT。

仓储在锁内读取最新 revision 后比较 ETag。匹配才构造和验证候选设置；不匹配返回 412，且无文件、运行时、AutoStart 或事件副作用。成功返回 200、完整新 snapshot、ETag 和 `operationId`。GET/PUT 与任何独立 FileRoots 写入口均必须通过同一仓储；若保留 `/api/config/file-roots`，其写操作同样属于一次逻辑设置提交，接受相同 If-Match/X-Operation-Id 并返回完整 versioned snapshot，不能再做独立读改写。

### API-ERR-01：稳定错误体

所有本设计新增或调整的 HTTP 失败使用如下 JSON；`message` 仅供展示，客户端只能匹配 `error` 和结构化字段：

```json
{
  "error": "settings_revision_conflict",
  "message": "设置已被其他客户端更新，请刷新后处理冲突。",
  "details": [{ "field": "revision", "code": "stale" }],
  "currentRevision": "42",
  "traceId": "...",
  "operationId": "..."
}
```

| HTTP | `error` | 副作用与客户端动作 |
|---:|---|---|
| 400 | `settings_validation_failed`、`invalid_if_match`、`invalid_cursor`、`cursor_scope_mismatch` | 零提交；保留草稿/已加载页，不自动重试。 |
| 404 | `root_not_found`、`path_not_found`、`launcher_item_not_found` | 刷新所属 snapshot；文件会话废弃。 |
| 409 | `settings_write_in_progress`、`directory_changed`、`launcher_operation_busy` | 没有 settings commit；按错误类型等待用户重试或从首页刷新。 |
| 410 | `cursor_expired` | 不返回 entries；废弃文件会话并从首页开始。 |
| 412 | `settings_revision_conflict` | 零副作用；进入 Settings conflict。 |
| 422 | `settings_partially_applied` | 不可证明已完全补偿；保留 journal，GET/恢复后人工确认，禁止盲目重放。 |
| 503 | `settings_apply_failed`、`settings_recovery_required` | 已证明未提交或已完全回滚；保留草稿，恢复后 GET 对账。 |
| 502 | launcher 命令稳定失败码 | 未将命令失败伪装为 busy；刷新 launcher runtime。 |

### API-FILE-02：cursor v2 严格全序分页

#### 协商与请求

客户端先读取 `/api/status.capabilities`。新 Agent 仅加性声明：

```json
{
  "settingsRevision": true,
  "fileListingCursor": true,
  "eventEnvelopeV2": true
}
```

字段缺失或 `false` 即不支持。只有 `fileListingCursor == true` 才发送 v2；否则使用既有 v1 offset 请求与响应，不依赖 Agent 版本字符串猜测能力。

v2 请求：

```http
GET /api/files?rootId=games&path=backup&pagination=cursor&limit=200
GET /api/files?rootId=games&path=backup&pagination=cursor&limit=200&cursor=<opaque-token>
```

- `rootId` 必须是 Agent 已配置根的稳定 ID；不存在返回 404 `root_not_found`。
- `path` 是相对于 root 的 canonical path：空字符串表示根；分隔符统一为 `/`，不接受 `.`、`..`、前导 `/`、尾随 `/` 或不能解析到 root 内的值。非法为 400 `invalid_path`，不存在为 404 `path_not_found`。
- 首页不得携带 cursor；后续页必须携带上一响应的 `nextCursor`，并原样复用**同一** `rootId`、canonical `path`、`pagination=cursor` 和 effective `limit`。
- `limit` 必须是十进制整数 `1..500`；缺省为 `200`。响应回显实际 `limit`。后续页变更 limit 是 400 `cursor_scope_mismatch`，而不是静默改变页边界。

#### 排序、cursor 字段与严格全序

v2 的每个可见条目只有一个排序键：

```text
K(entry) = (
  kindRank,                         // directory = 0，非 directory = 1
  name.OrdinalIgnoreCase,
  name.Ordinal                      // 消除大小写同键，形成严格 total order
)
```

目录内名称是唯一的；末尾 Ordinal tie-breaker 仍是强制要求，以确保比较器对任意返回条目严格、稳定、可测试。服务端对首页选择最小的 `limit + 1` 个键；对后续页选择严格大于 cursor 最后键的最小 `limit + 1` 个键；返回前按 `K` 升序排列。第 `limit + 1` 项仅用于决定 `hasMore/nextCursor`，不能同时出现在本页 entries。

cursor 对客户端完全 opaque：客户端不得解析、拼接、修改或跨请求复用。受保护 token（签名并防篡改；实现可采用加密保护）在逻辑上至少包含：

| 字段 | 用途 |
|---|---|
| `format = 2`、`keyId` | 版本识别和密钥轮换。 |
| `rootId`、canonical `path` 或不可逆 scope fingerprint | 绑定目录范围。 |
| `sortId = directory-first-name-ci-name-ordinal-v1` | 固定排序算法，算法变化不可误续页。 |
| `effectiveLimit` | 固定会话页边界。 |
| `lastKey = (kindRank, nameCI, nameOrdinal)` | 下一页严格 `>` 的下界。 |
| `directoryIdentity`、`directoryChangeStamp` | 绑定同一目录对象及已验证的未变更版本。 |
| `issuedAt`、`expiresAt` | 限制 token 存活期；默认 TTL 10 分钟。 |

token 不得在明文中泄漏绝对路径、根物理路径或其他配置内容。响应中的 `directoryVersion` 是同一 `directoryIdentity/changeStamp` 的不透明诊断标识，不可用作 cursor；`nextCursor` 为 `null` 当且仅当 `hasMore == false`。

```json
{
  "schemaVersion": 2,
  "entries": [
    { "name": "A", "kind": "dir", "size": null, "modified": "2026-08-02T00:00:00Z" }
  ],
  "nextCursor": "opaque-or-null",
  "hasMore": true,
  "limit": 200,
  "directoryVersion": "opaque-directory-version"
}
```

#### 目录变化、过期与“无重不漏”边界

v2 的“无重复、无遗漏”保证只针对**同一 directory identity、同一 change stamp、同一 root/path/limit/sort 和未过期 cursor 链**。服务端在处理每个带 cursor 请求时：

1. 验证 token 签名、格式、TTL、root/path/sort/limit scope；
2. 在枚举前检查目录 identity/change stamp 与 token 一致；
3. 用严格 `K > lastKey` 谓词选择本页；
4. 在枚举后再次检查目录 identity/change stamp；
5. 仅两次检查都一致时返回页面和下一 token。

任一前后检查发现目录变更、替换或不可证明稳定，返回 `409 directory_changed`、零 entries、零 nextCursor；客户端丢弃整个会话并从首页启动新 generation。TTL 到期返回 `410 cursor_expired`；解码、签名、版本或字段非法返回 `400 invalid_cursor`；root/path/limit/sort 与 token 不一致返回 `400 cursor_scope_mismatch`。这些失败不会返回部分页，因而不会把“变更目录中可能重复/遗漏”的结果伪装为连续列表。

在目录不变前提下，严格全序与 `>` 分割使首页及每个后续页构成不相交、有序分区；`limit + 1` 的 look-ahead 只移动边界项到下一页，故可由串联所有 pages 后与一次全量严格排序的集合相等来验证“每项恰好一次”。目录变化时故意中断链而不是承诺不可能的快照语义。服务端无需物化所有可见条目：以容量 `limit + 1` 的选择结构保持候选，额外内存为 `O(limit)`；单页 CPU 仍可能为 `O(N)`。

v1 不改变既有 DTO 与 offset 行为。v1 客户端仍应有单页在途与 generation 防护，但不得获得 v2 的无重不漏声明或精确 total 新承诺。

### EVT-01：Event Envelope v2

当 `eventEnvelopeV2 == true` 时，所有业务事件使用以下加性 envelope；现有 `type`、`timestamp`、`payload` 保持：

```json
{
  "schemaVersion": 2,
  "eventId": "f1f14326-7fc0-4ece-a9cf-c9eea776f7e7",
  "agentInstanceId": "uuid-per-process-start",
  "sequence": "1034",
  "operationId": "5ec8b1a7-8090-4f4f-a3a1-47d696f1f324",
  "type": "settings.updated",
  "timestamp": "2026-08-02T00:00:00Z",
  "payload": { "revision": "42" }
}
```

`schemaVersion` 为整数 `2`；`eventId`、`agentInstanceId` 为 UUID；`sequence` 是十进制字符串；`operationId` 可为 null。每次 Agent 进程启动生成一个 `agentInstanceId`。业务事件由单一串行发布管道分配递增 sequence 并按该序列向单条 connection 写出；ping/pong 不占 sequence。这样 sequence 在一个 instance 内定义严格发布总序，但不承诺跨 instance、跨断线或跨 connection 的可恢复顺序。

`settings.updated.payload` 至少包含新 `revision`，并且 event 的 `operationId` 与成功 PUT 相同。成功提交的 PUT 响应、持久化 snapshot 与该事件必须是同一 revision；验证失败、完整回滚失败响应、恢复中的写入都不得发布成功事件。

客户端规则：同 instance 的 `sequence <= lastSeen` 丢弃；跳号触发合并 HTTP 对账；instance 改变触发全量可见域对账；无 v2 元数据的 v1 事件按 type 保守失效。未知事件或未知字段不得断开连接。PC Web 失效 settings/launcher/files/power/audio 的对应 query；Android 将 SharedEventStream 的 reconnect/instance/gap 转成 epoch/Flow，由可见 ViewModel 各刷新一次。任何对账均不得重放关机、上传、删除、rename、move 或 settings PUT。

### API-SET-02：统一仓储与提交顺序

`AgentSettingsRepository` 是唯一逻辑设置写入口。每个请求、Avalonia settings host、Tray 自启切换及 FileRoots endpoint 都调用它；仓储以进程内 `SemaphoreSlim` 串行化，等待超过 3 秒返回 `409 settings_write_in_progress`。读取可使用最后确认 snapshot，但提交必须锁内重读。

用户配置加性保存 metadata：

```json
{
  "SettingsMetadata": { "Revision": "42" },
  "Launcher": {},
  "FileRoots": [],
  "RemoteShutdown": {}
}
```

提交按下列不可重排步骤执行：

1. 获取 gate，确认未处于 `recovery-required`，锁内重读配置和 revision；
2. 检查 If-Match；不匹配立即 412 且零副作用；
3. 将 patch 应用于完整候选 snapshot，做全部 settings/launcher/file-roots 交叉校验；校验失败 400 且零副作用；
4. 写入同目录 prepared journal：`operationId`、phase、previous config bytes、previous/desired AutoStart、previous/candidate revision、时间；flush journal；
5. 用同目录 temp + flush + atomic replace 写 candidate config；
6. 由 `SettingsRuntimeApplier` 应用 AutoStart 和进程内配置投影；
7. 成功时删除 journal、发布 `settings.updated`、返回 200 full snapshot；删除 journal 与发 event 均只能在成功运行态后发生。

启动时、HTTP 接入前运行 `RecoverPendingSettingsTransactionAsync()`。它优先恢复 previous confirmed config 和 previous AutoStart；成功后清除 journal。任何不能证明恢复完成的情形都保持 journal、切到 `recovery-required`，所有 settings 写返回 503，直到受控恢复完成。journal 是恢复资料，不是新的业务事实来源。

## 运行时与失败模式

### 配置提交、补偿与响应判定

| 失败点 | 必须动作 | 响应 | 事件 |
|---|---|---|---|
| gate 超时 | 不开始提交。 | 409 `settings_write_in_progress` | 无。 |
| If-Match/校验失败 | 不写 journal/config，不调 AutoStart。 | 412/400 | 无。 |
| journal/config temp/replace 失败 | 清理可安全清理的 temp；确认旧 config 未变。 | 503 `settings_apply_failed` | 无。 |
| AutoStart/运行态 apply 失败且 config 与 AutoStart 都已证明恢复 | 先恢复 config，再恢复 AutoStart；journal 清除。 | 503 `settings_apply_failed` | 无。 |
| apply 或补偿任一步无法证明 | 保留 journal，阻止后续 PUT，记录 phase。 | 422 `settings_partially_applied`；若启动恢复中则 503 `settings_recovery_required` | 无成功事件。 |
| 全部成功 | 删除 journal，返回同一 revision snapshot。 | 200 | 恰好一个 `settings.updated`。 |

网络超时并不等于提交失败：客户端保留 draft，GET `/api/settings` 对账 revision 与内容；禁止自动重发同一 PUT。`operationId` 用于把 HTTP、日志和事件关联，不承担幂等语义。若 AutoStartManager 无法读取并证明最终 Task Scheduler 状态，仓储必须把相关失败归为“无法证明”的 partial applied，而不能报告完全回滚。

### 文件与实时失败

- `invalid_cursor`、scope mismatch：保留已接受 entries，但不继续该 cursor；用户刷新才创建新会话。
- `directory_changed`、`cursor_expired`、root/path 404：废弃会话和旧 nextCursor，提示首页刷新；不追加任何返回项。
- v2 event gap、instance change、reconnect：合并一次按域 GET；事件重复或逆序不得导致多次 mutation 或页面回退。
- Launcher busy 是 409；真实命令失败是 502，客户端随后刷新 runtime status。

## 安全与隐私

本期不修改安全策略。以下是为保持既有边界而必须遵守的约束：

- ADR-01 不产生跨 origin XHR/WS，也不借 URL 输入扩大 Agent 可达范围；最近目标仅保存展示/导航元数据。
- cursor token 必须防篡改且不泄露 root 的物理绝对路径、用户配置或凭据；非法 token 统一分类错误，不回显 token 内容。
- `traceId`/`operationId` 仅用于诊断与关联；错误 body 不返回异常栈、配置 bytes、Task Scheduler 命令或敏感路径。
- 远程关机的确认是 UX 防误触，不是认证或授权边界；本设计不添加 token/password 输入。

## 兼容性与迁移

### 能力矩阵

| 契约 | 旧 Agent | 新 Agent + 旧客户端 | 新 Agent + 新客户端 | 新客户端回退到旧 Agent |
|---|---|---|---|---|
| settings revision | 无 revision/ETag | 忽略加性字段；在兼容窗口允许无 If-Match 写 | capability 后带 ETag If-Match，412 可见 | 显示“条件写保护不可用”，用户确认后才执行兼容写。 |
| event v2 | v1 type 失效 | 未知字段可忽略 | instance/sequence/gap 对账 | 缺元数据时按 type 保守刷新。 |
| cursor v2 | v1 offset | 旧请求/DTO 保持 | capability 后 `pagination=cursor` | 丢弃 session，从 v1 首页开始。 |
| Power IA | 不涉及 Agent 协议 | Android 旧导航不受 Agent 影响 | 五 Tab + Admin 二级 Power | 回退 APK 仅改变入口，不影响关机 endpoint。 |

缺失 capability 一律按 false，禁止根据版本字符串、响应里“刚好有 revision”或异常探测决定协议。新 Agent 必须持续接受 v1 files 请求；旧客户端看见 v2 event 的附加字段不得失败。

### 发布顺序（MIG-01）

1. 先发布向前兼容 Agent：metadata/revision、GET ETag、宽容的 legacy If-Match 处理、统一仓储、v2 event 字段、cursor v2 和 capabilities；v1 行为保持。
2. 在临时配置目录完成 Agent 条件写、并发、故障注入、恢复和 cursor 10k/50k 契约测试；再以旧 PC/Android 验证未知字段与 v1 请求。
3. 发布随 Agent 静态包的 PC Web：同源导航、target-key、draft、Launcher、capability fallback 和对账。
4. 发布 Android：五 Tab/Admin 二级 Power、文件 session、reconnect Flow、v2/v1 fallback。
5. 观察结构化计数：无 If-Match 写、v1 offset、412 conflict、cursor 409/410、recovery journal、partial applied 和 event gap。兼容窗口结束、是否拒绝缺 If-Match（428）以及 v1 退役必须另行批准；本设计不预设日期。

## 可观测性

每次 settings 提交记录 `traceId`、`operationId`、received/committed revision、If-Match 结果、journal phase、补偿结果和稳定 error code；不得记录配置 bytes、opaque cursor 或敏感绝对路径。事件发布记录 instance、sequence、type、operationId 和发送失败统计。

文件分页记录 schema version、limit、响应条数、是否有下一页、cursor 错误类别、目录变化中断和耗时；不记录 cursor 明文。性能报告至少包含机器规格、磁盘类型、Agent build、数据集、10 次原始样本、p50/p95/最大值和峰值额外内存。

历史 UI 台账是治理产物而非 telemetry：每项必须链接现有/新复验证据，明确“未重开”的理由、已知阻断和下次复验触发条件。

## 回滚

| 对象 | 回滚动作 | 前提与限制 |
|---|---|---|
| PC Web 静态 bundle | 替换到上一个已验证 bundle。 | 新 metadata 被旧前端忽略；不会自动撤销已成功业务设置。 |
| Android APK | 发布上一受支持版。 | 旧 APK 仍可对新 Agent 用 v1；Power 入口回退不改变 Agent 状态。 |
| Agent 二进制 | 优先仅回滚代码，保留 additive config metadata。 | 任何未完成 journal 必须先由新版本恢复或明确阻断；旧 Agent 不得接管 pending journal。 |
| cursor v2 | 关闭/撤销 `fileListingCursor` capability 后客户端丢弃 v2 session，回到 v1 首页。 | 不复用 v2 cursor 作 offset。 |
| settings 条件写 | 在兼容窗口内撤回 capability 并允许 legacy 无 header 写。 | 客户端不得自动把一个失败的条件写改发为无条件写；需用户确认。 |
| 已成功设置/AutoStart | 使用成功前 snapshot/备份经一次新提交手工恢复，并记录 operationId/revision。 | revision 不是业务撤销；不可用二进制回滚自动撤销外部副作用。 |

## 测试策略

以下为实现前必须落地的可验证要求；测试编号以关联测试设计为准，若其路径或编号治理后变化，应保留可追溯映射。

| 主题 | 最低契约测试 |
|---|---|
| ADR-01 | 任意历史 store 值下，HTTP/WS 均是页面 origin；切目标调用 `location.assign` 并保留 route；旧 target 的延迟响应不写新页。 |
| ADR-03 | BottomNavigation 恰好五项；管理风险卡可达 Power；返回 Admin；无连接/能力缺失/未确认均零 POST。 |
| settings 条件写 | GET body revision 与 ETag 一致；两个同 revision PUT 恰好一个 200、一个 412；非法 If-Match 400；无 header legacy 行为仅在兼容配置下可用。 |
| 仓储恢复 | Settings/FileRoots/本机 UI 并发都经过 fake repository；校验与 IO 失败零副作用；AutoStart 可补偿失败恢复；不可证明补偿保留 journal、阻止 PUT；成功事件一次且 revision 对齐。 |
| event v2 | 同 instance sequence 严格递增；重复/逆序丢弃、gap/instance/reconnect 各只触发受控 HTTP 对账；v1 event 仍按 type 失效；不重放 mutation。 |
| cursor v2 | 对 10k/50k 含目录、大小写和 Unicode 条目，串联未变目录的全部页与一次严格排序完全相等、无重复；边界项只在下一页；root/path/limit scope 错误 400，篡改 400，过期 410，目录前/后变化 409 且零 entries。 |
| 资源 | 每页额外内存随 `limit` 而非 N 增长；记录 p50/p95。若目标环境不达测试策略阈值，登记 Spike-FILE-01，不临时加索引。 |
| 兼容/回滚 | 旧/新 Agent、PC、Android 的矩阵；pending journal 回滚演练；客户端不自动降级重试条件写。 |
| 历史 UI | HUI 台账逐项复验现有证据；只对失败项建立独立问题，不批量重开。 |
