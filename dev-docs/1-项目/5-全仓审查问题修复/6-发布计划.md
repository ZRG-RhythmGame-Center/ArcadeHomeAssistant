# 全仓审查问题修复发布与验收计划

这是未来候选版本的发布与验收编排，不是发布批准。AC 以[验收标准](3-验收标准.md)为准，协议以[技术设计](4-技术设计.md)为准。

## 发布范围

候选仅可包含已通过 P0 的同源 PC Web、Android 五 Tab/Admin 二级 Power、Settings 并发保护、event v2、cursor v2/v1 回退、Android 文件会话和 Launcher。当前尚未开始 P0 实现，也未形成候选提交；基线恢复不等于候选可发布。安全策略、CORS、认证、数据库和目录索引不在范围内。

## 灰度与开关

先发布向前兼容 Agent，再发布随 Agent 静态包的 PC Web，最后发布 Android。`settingsRevision`、`eventEnvelopeV2`、`fileListingCursor` 均以 `/api/status.capabilities` 为唯一协商依据；字段缺失或 false 按旧行为。不得根据版本字符串猜测能力。兼容窗口、密钥轮换与退役日期尚未批准，发布前必须版本化记录。

## 迁移

保留 v1 files offset 和无 v2 metadata 事件消费。新客户端遇旧 Agent 时：Settings 显示条件写保护不可用，必须用户确认才可兼容写；文件丢弃 v2 会话后从 v1 首页开始；事件按 type 保守失效。禁止把失败条件写自动重发为无条件写。

## 监控

记录候选 SHA、产物 hash、环境、无 If-Match 写、412、409/410 cursor、pending journal、partial applied、event gap、v1 offset 使用和 socket 数。不得记录配置 bytes、绝对路径或 opaque cursor。性能原始 CSV、内存、HTTP/WS transcript 作为候选证据保存于受控非提交位置。

## 回滚

PC bundle/Android APK 回滚到已验证版本；Agent 优先仅回滚代码并保留 additive metadata。存在 pending journal 时旧 Agent 不得接管；先由新版本恢复或阻断。撤回 cursor capability 后客户端从 v1 首页开始；回滚 binary 不会撤销已成功设置或 AutoStart 副作用。

## 沟通

发布记录必须列出候选 SHA、兼容矩阵、未通过或豁免项、设备/ABI、已知限制、回滚负责人和证据位置。P0 失败、flaky、缺证据或环境阻塞时明确“拒绝发布”。

## 完成条件

1. 基线测试阻断已关闭并有复跑证据；随后 AC-01～08 及 P0 测试必须全部通过。基线恢复不能替代任何 P0 通过条件。
2. `fileListingCursor=true` 时，严格全序、scope、目录变更和 10k/50k 证据齐全；false 时保存 capability 与 v1 结果。
3. Android arm64 和交互式 Windows/浏览器人工项有实际证据；未具备环境即阻断，不以模拟器替代。
4. 仅在运行后记录结果：`pnpm --dir apps/pc-web test/typecheck/lint/build`、Android Gradle 单测/JaCoCo、Agent `dotnet test`、发布脚本、`docctl validate --root dev-docs`、`git diff --check`。

## 下一阶段前置

基线测试阻断现已关闭。下一阶段依次为：隔离当前工作树、明确工作树所有者、记录候选提交 SHA，再开始 P0 实现。未完成这些前置时，不得将任何并行工作区改动计入 P0、候选版本或发布证据。

## 已知限制

本计划仍要求实际 arm64 设备、交互式 Windows 与双 origin 浏览器证据；模拟器或 Robolectric 不能替代这些环境。10k/50k 等大目录验证、性能原始数据和目录扫描影响也仍待候选阶段实测。以上限制存在时，发布门禁保持关闭。
